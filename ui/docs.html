What nnstudio is

nnstudio is a workbench for neural networks. You compose a network on a canvas out of boxes — each box is one piece (an embedding table, a matrix multiply, an activation, a tokenizer…), and wires between boxes carry the data. When you run the canvas, numbers flow along the wires, box by box, and whatever comes out of the last box is the answer.

The same canvas does both jobs: it runs a network (feed it text or numbers, watch the outputs) and trains one (give it a dataset and a loss, and it improves its boxes). A canvas is stored as plain JSON — a design — so you can save it, share it, and load it back exactly as it was.

Three things make the app practical rather than toy:

  • Real models. Load a .gguf from Import ▾ (or point an hf box at a Hugging Face repo) and the app builds the whole network for you — hundreds of boxes, wired exactly like the model's original implementation. You can then look inside it, change it, or train on top of it.
  • A real backend. The heavy maths runs on a backend service (your GPU, CPU, or a remote machine) — the browser only draws and edits. The Backend ▾ menu connects them.
  • Tasks. Long work — training, big jobs — runs as a task managed through the agent box: it shows progress live, and can be paused, detached (checkpointed and stopped), and resumed later.
The rest of this handbook is two halves: everything about using the app (the canvas, the boxes, recipes), then two short theory sections — how networks work and how training works — written just deep enough for the boxes to make sense. If you already know what a loss is, skim them.

The canvas: using it

Above the canvas, a browser-style strip of project tabs: one tab per open canvas, titled with its project name (New Project 1 for a blank), a * when there are changes the server has not seen, and a + at the right that offers New Canvas (a fresh blank, nothing saved yet) and Saved Canvas … (your saved canvases — each opens as its own tab). Ctrl/Cmd+S saves the active project: a new one asks what to name it first; a saved one saves silently (same name, replaced). Below the strip, the toolbar's menus: Palette ▾ Import ▾ Backend ▾ VRAM ▾ — the server config's door is the first row of the Backend menu (show the server config).

Moving around

  • Add a box — open Palette ▾, expand a category, and drag a card onto the canvas. Categories follow the boxes' jobs: AI, weights, text, Dataset, tensor ops, blocks, analysis (the heatmap), and containers.
  • Bring a model in — Import ▾ → GGUF model … opens one pop-up with the machine's .gguf files, each recognized by its own header. Importing adds one nested box with the file's structure inside — a model its blocks, a vision encoder (mmproj, shown as such) its tower. It never makes a canvas and never adds boundary boxes: the rest of your design stays exactly as it is, and cancelling leaves it untouched too.
  • Add training data — the Palette's Dataset ▾ category holds the dataset box. Right-click it any time to set the rows ….
  • Move / resize — drag a box by its body; drag its corner to resize (the display boxes — input, output, dataset, agent — resize with their window). The input and output boxes open roomy by default, so their content has the space; double-click one for the compact size, drag its corner for anything in between.
  • Wire two boxes — drag from a box's right dot (its output) to another box's left dot (its input). Hover a wire to read the data riding it — its type (matrix, image, text, ids…), its dtype and its shape. A shape the wiring declares reads [? × width]: the first axis is the batch, and only a run knows its size — what you type into an input box, and what a run actually left, are exact. The same hover on an input or output box names it and says what it emits or expects; a custom box shows the input/output boxes its dots stand for (hover one dot to read just that box). Right-click a wire to reshape or remove it.
  • Edit a box — right-click it. Its menu renames it (the server config excepted), changes its settings (the activation, the operation, the embedding…), and offers freeze (keep its weights fixed) and off (skip it on runs).
  • Step inside a model — double-click a model box (palette → models). A nested box is a whole network of its own — that's the "nested" in nnstudio, and a model is where the trainable weights live. Double-clicking again goes deeper; the strip above the canvas shows where you are and takes you back.
  • Run it — connect Backend ▾ first, then press ▶ run the design in an input box. The page verifies the dataflow first — a wired path from an input to an output — then the backend computes it: the wires light as the data goes, and only the boxes on that path take part: a spare model, a half-built branch or an input nothing reads is discarded — neither marked nor sent to the backend, and each data box shows what it received (the output shows its own). A run is inference: no gradients are kept (the lightest run — dataset boxes stay idle).
  • Train it — training is scored on the output box and wired through the input box. Open the output, switch its window to the training tab and see where it lives: the architecture sits in a model box (palette → models) and a train config box names it. The config carries every knob of the run (the paradigm, the optimizer, the learning rate, the batch, the steps, the save/eval cadence, the optional test split) and its own data dot: one dataset — or a select col box — feeds the run, and the config detects it: its window shows the columns it hands out and x col / y col pick them there (A/B by default). The run enters the model's first input and scores its first output. The controls (start, save now, hold, detach, resume, load last checkpoint) sit under them, with the plan's summary, the step/loss strip and the live curves. The output is what the training scores; in rl it is the policy the run samples from. Training keeps gradients on the non-frozen weights, and the run reports the loss (and accuracy) on the dataset's rows. Each run leaves its numbers on the boxes (click a box to see the values that passed through it).
  • Price it — VRAM ▾ shows how much memory the design's weights need and where they will live (GPU or system). Freeze nothing, move everything, see it change.
The whole idea, in one line: boxes hold the pieces, wires carry the numbers.

Designs, saving, sharing

Everything on the canvas is a design — plain JSON. Right-click the canvas → the design exports it (a .json file), imports one back, and exports the whole design's weights. Design JSON nests: a nested box carries its own network inside the file, so one file can hold a whole model. There is no autosave: the tabs live in this page, so a reload starts a fresh New Project 1 — Ctrl/Cmd+S is how a design outlives it (saving takes an account, below).

Everyone starts a guest. A guest draws, wires and runs like anyone; what a guest never gets is the server keeping the design. That is what the user block at the top right (the icon and the name — guest to begin with) is for: create an account puts one Cloudflare bot check in the way (you solve it in the dialog), asks a username and an optional email (sealed like everything else), then this browser makes a token — 32 random bytes, shown once — and the token is the whole login. Anywhere else, log in with a token and paste it. Signed in, Ctrl/Cmd+S saves the active project — sealed in this browser first — and the + beside the tabs lists what was saved, each opening as its own tab; saving over a name replaces it. The account menu keeps the account itself: who is signed in, unlock, log out.

The server cannot read any of it. The token never leaves the browser: an auth credential is derived from it (the server keeps only a hash of that), a keyed name tag lets rows be keyed and duplicates refused without the server learning the name, and an AES-GCM key seals every name and design before it is sent. users.db is therefore a pile of ciphertext plus the times and sizes — nothing of it is in git. The browser remembers the token so a reload stays unlocked; log out forgets it, and without it the account shows locked (account 🔒) until the token is pasted into unlock with your token …. Lose the token and the saved designs are gone for good — there is no reset, the server included. Sealing needs WebCrypto, which lives on secure origins only: http://localhost or https. A machine that should be reached from other devices over plain http can mint a certificate from a tiny local authority (tools/tls_local.sh) and trust its ca.crt once on each device — then https://<address>:8124 works the same.

The bot check uses Cloudflare's test keys until NNSTUDIO_TURNSTILE_SITE_KEY and NNSTUDIO_TURNSTILE_SECRET_KEY name a real widget — the dialog says which is in use. Make one at dash.cloudflare.com → Turnstile → Add widget (the hostname you use; localhost works), put the two keys in the repo's .env and restart the service. NNSTUDIO_COOKIE_SECURE=1 adds the Secure flag to the session cookie for an https deployment.

The boxes: reference

Every box shows its name, its shape (what comes in and goes out), and — if it holds weights — its weight count. Below: what each box does, the fields you can set (right-click → set …), and what wires into or out of it.

Data boxes — getting things in

input
0 in · 1 out

Where data enters the network. An input box is what a run feeds — one per thing you want to test, and its data rides with the design: the run hands it to the backend, and the output shows exactly what arrives. Its own window holds the editor — a data dropdown (matrix / text / image) and the data itself, typed right on the canvas: a matrix is one row per line, numbers split by spaces or commas — one line is a vector (1 2 3), two lines a 2-D matrix (whole numbers stay whole, ids and all). In image mode you pick a picture from your machine — or just drag & drop a picture onto the box, or paste one (with the box selected, or into the box's drop zone). The box shows the thumbnail it received, and the picture lives in the project's media store (the same blob: store the dataset sheet uses). The picture itself travels the wires as a matrix of RGB channels (h × w × 3, 0..1): any box that receives it draws it as a thumbnail (an output box shows the image, and a vision tower does its own resizing, normalization and patch cutting). The window also carries the ▶ run the design button — the run starts where the data is — with the run's verdict line under it. (Inside a nested box, an input or output is only a box: the boundary's port. No editor, no readout, no run button — the value comes from the parent box's dot, and all a nested design does is move data through.) The editor opens roomy (its content has the space); double-click the box for the compact size, or drag the corner to size it yourself.

New designs train through a model box: the train config names the model and carries the data, and the batch enters the model (an empty input box wired into it stands down on a training run). Inputs stay what a run feeds — the value you type here rides the wires.

Older designs (built before models) keep their training dots: training on, the input grows one for the train config and, once wired, one for the matrix — a dataset or a select col box. They run exactly as they did; right-click a weight box → wrap the weights into a model moves them to the new shape.

Fields: width dout (a matrix's columns — what a layer reads); data type input_mode — matrix (the numbers it carries, one row per line), text (a string — wire it into a tokenizer), or image (a picture, resized to the model's own geometry); the numbers, the text, or the blob: reference itself; for images the side the pixels are sent at (image_size), set for you when a vision tower is loaded. The backend builds a matrix input's tensor from the box itself (the run's feeds still win when an API client sends its own).

tokenize
1 in (text) · 1 out (ids)

Turns text into token ids — the numbers a network actually reads. With a wire in, it tokenizes whatever arrives; without one, its own text. Usually made as a pair: right-click the canvas → text → load a tokenizer … asks for a Hugging Face repo and lands both the tokenizer and its de-tokenizer, the one repo bound to each.

Fields: repo (a Hugging Face tokenizer) or vocab (a simple one-character-per-token vocabulary, great for teaching); optional default text.

dataset
0 in · 1 out (labels → loss)

Your training data. Each row is a prompt and a completion — what the model reads, and what it should learn to write. A training run feeds its rows to the loss box; the prompt part of each row is masked out of the loss (the model learns to produce the completion, not to parrot the prompt).

Its face is a dataframe sheet inset in the card, like a pandas table or a CSV, with a single header row: each column shows its name, which defaults to the column's letter (A, B, …) — click a name to choose one, and emptying it puts the letter back — and a type chip (int64, float64, bool, object, image, video) inferred from the values, click to override. Click a cell to type (Enter moves down, Tab right), paste a block from Excel/Sheets, + row / × manage rows, and hovering a column's name shows + / × to add or remove it; dragging the header edge resizes the column. Double-click the box for more room.

A column can hold images and videos: drop a file on a cell (or paste one) — the bytes live in the project's media store, the cell carries only a small blob: reference, and the table shows the thumbnail (click to view or play). The box menu exports the table: a plain .csv for text and numbers, or a .zip (csv + media) when cells hold media — and imports either back. A file-backed dataset previews its first rows (read-only) from the backend.

Fields: text (rows typed in) or file (a JSONL file path on the backend machine); tokenizer repo/vocab, like the tokenize box. One row per line: JSON like {"prompt": "…", "completion": "…"}, or prompt<TAB>completion. The sheet keeps both formats verbatim — JSON rows keep their extra keys.

select col
1 in (a dataset) · 1 out (a matrix)

A dataset's columns, as a matrix: the select col box reads one sheet — wired in, or bound in its window — and hands out [rows × columns], the shape the input's data dot takes. Wire it into that dot and the run reads those cells, row by row; the train config detects them and picks x col / y col from the columns it hands out. A blank column list takes every column; a single column of text tokenizes as usual; several columns are a numeric vector per row (x0 x1 x2 — three columns are a 3-wide input). Columns are named from the sheet's header, or by letter (A, B, … = position); the window shows the shape it hands out, and says when a name is not in the sheet.

Fields: dataset (the sheet it reads), cols (the columns it selects — names or letters, a sequence is a vector, blank = every column).

Compute boxes — the network itself

embed
1 in (ids) · 1 out (vectors)

A lookup table: every token id becomes a learned vector. It is the bridge from discrete tokens to the continuous numbers the rest of the network works in. (Word embeddings are the classic "what does this word mean as a direction in space" representation.)

Fields: vocab (table rows), din/dout (vector width), embed_scale (Gemma-style scaling); the weight binding t and dtype.

layer
1 in · 1 out

The workhorse: multiply the incoming numbers by this box's weight matrix (plus a bias). Stack enough layers and the network can fit very complicated patterns. This is where nearly all of a model's weights live.

Fields: din/dout; weight binding t; dtype. Uncheck nothing — a layer not frozen is trainable.

act
1 in · 1 out

An activation — a small bend applied to every number. Without one, a stack of layers collapses into a single layer; activations are what give depth its power. Attention scores also pass through here.

Fields: the function act (silu, relu, tanh, softmax…); gain (a scaling factor, e.g. attention's 1/√d); causal (a "never look at future tokens" mask).

norm
1 in · 1 out

Keeps the numbers flowing through the network on a sane scale (deep networks drift into huge or tiny values otherwise). Every modern model sprinkles these between its compute boxes.

Fields: norm — rms or layer; eps; size; zc.

op
1–2 in · 1 out

One mathematical operation — anything else the network needs. Two-input ops (add, matmul, concat…) take wires into both dots; one-input ops take one.

Fields: the operation op: transpose, dot product, matmul, concat, add, subtract, multiply, divide, rope, scale, topk, conv1d, scan, reshape, permute, repeat, mask, slice, zeros; plus each op's own settings (dims, axes, theta, window, head geometry for attention…). A slice is told axis and either index — one slot, that dim disappears (-1 is the last one, so a [7 × 5120] of tokens becomes the last token's [5120]) — or start/stop, which keep a range of that axis.

script
1 in · 1 out

A box you program yourself: a short Python expression over its input (x) returning a tensor. The escape hatch for anything the other boxes don't cover. The code travels inside the design file.

Fields: script.

model
its own inputs · its own outputs

The architecture's box. Every trainable weight lives inside one: the palette refuses embed / layer / norm and the other weight boxes at the top level, and building inside a model is the only way. Top level stays what it should be — sources, the model, sinks, and the training that points at it.

A model is a nested box with a skeleton inside (input → output) and a tag that says what it is. Its dots are its inner input/output boxes (in the order they sit); its window reads the ports, the parameters, whether any weight is frozen, and which train config names it. Double-click to step in and build — layers, blocks, another model. Out here it is one box you feed and read.

Designs built before models — weights sitting flat on the canvas — keep running, and one click moves them in: right-click a weight box → wrap the weights into a model (or the link in a config's window). The wrap moves the cluster inside, makes the boundary dots, and lands the wires where they were; the old training wiring folds onto the new config.

Fields: model (the tag that makes it a model), inner (the network inside), the weight bindings like any nested box; box size.

custom
its own · 1 in · 1 out

A nested box: a whole network inside one box. Double-click to step in and edit its insides; from outside it behaves like a single box. This is how large models stay legible — a 27-billion-parameter model is one nested box that you can open into blocks, each block open into its attention and MLP. Tagged as a model (palette → models), it is where trainable weights live.

Fields: its inner network; where its weights read from (file, t), and the source repo when it came from a huggingface canvas. A whole model arrives through Import ▾ → GGUF model … — it lands as a new nested box; to change it, delete the box and import again.

Result boxes — getting things out

heatmap
1 in (a vector) · 1 out (a picture)

Draws a vector as one picture: whatever reaches it is flattened, centred on its median and spread by its robust deviation (1.48 × the median absolute deviation — the ramp then covers ±2 of those, and anything beyond clips to its ends), and laid out on the most square grid its count allows (96 values → 12×8), through a five-stop colour ramp — blue (low) → cyan → green → yellow → red (high), so the middle colour is the vector's typical value. One value moving moves one cell, never the whole picture — similar vectors draw similar pictures. A length with no square-ish factor pair (a prime) gets a near-square grid whose padded tail reads neutral gray — never an invented value. The picture is an ordinary RGB matrix in 0..1, so it reads as an image everywhere: its own window draws it after a run (with copy/save at hand), and an output box at the end of the wire shows it too. Feeding it a bigger matrix? Everything is flattened — put a slice in front to picture one row.

Fields: width din (the vector's length — a wire settles it), display box size.

output
1 in · 0 out

The end of the line: its own window shows whatever data reaches it — the numbers it received (with the shape and mean under them), or the text it produced — and says no data yet until a run. Its expected type and shape come from its wire, not a stored number: with nothing connected it reads ?, a matrix wire reads matrix [? × 5120], a text wire simply text. When the data is a picture, it is drawn right there, with copy image (onto the clipboard) and save image (a download named after the box — the stored file's own format, or a PNG re-encoded from the run's thumbnail) under it. Name outputs after what they are (logits, hidden) — runs report per output name. The window opens roomy; double-click the box for the compact size, or drag its corner to size it yourself.

Its window has two tabs: output (the readout) and training. In the model world the training tab is the readout's own — it says where training lives and offers the chip that drops a train config beside the model. Older designs (built before models) keep the full tab: Enable Training, the plan, the step/loss strip, the controls — start, save now, hold, detach, resume, load last checkpoint — and the live curves.

Fields: din, its name, train (the training tab), task_id (the live task), display box size, panel.tab. Older designs keep their stored training fields (dataset, x_col, y_col, …) — the engine reads them, and a train config box moves the settings forward.

detokenize
1 in (ids) · 1 out (text)

Token ids back into text — the inverse of the tokenize box. Put it after a sample box to read what the model produced. Usually made with its tokenizer: right-click the canvas → text → load a tokenizer … lands the pair, one repo for both.

Fields: repo/vocab — must match the tokenize box that fed the model.

sample
1 in (logits) · 1 out (ids)

Picks the next token from the model's scores (logits). This one box is the difference between "a network that computes" and "a model that writes": generation is sampling a token, feeding it back in, and repeating.

Fields: temperature (0 = always take the best token; higher = more adventurous), sample_seed (reproducible picks).

loss
2 in (logits, labels) · 1 out (scalar)

Measures how wrong the model is — one number, lower is better. It compares the model's scores against a dataset box's labels. During training this is the number that falls. Its output is a plain scalar, so you can wire it anywhere and watch it.

Fields: loss (the kind — cross-entropy for next-token prediction).

reward
0 in · scores texts

A deterministic score for a piece of text — "how good was this output?". It doesn't run inside the dataflow; a training run applies it to generated samples. The same pair of prompt and output always earns the same score: exact match against a target, a regex pattern, a length budget, or your own Python expr over prompt and output. This is the hook for reinforcement learning: the reward says how good, the training raises it.

Fields: reward (python/exact/regex/length), expr, pattern, match, limit.

System boxes — models and long work

hf
0 in · text result

A complete Hugging Face model, run by the backend as a whole — no wires needed. The quick way to get a baseline answer (or a reference for your own canvas to match).

Fields: repo, a prompt text, temperature.

agent
none — a window, not maths

A live window onto a task — a long-running job managed by the backend agent (research, big jobs). It shows the task's stream as it works, with its progress ring on the card. This is the app's one surface for firing and managing tasks: start one here, pause it, cancel it, read what it did. Double-click the box to grow or shrink its display.

Fields: task_id (its task), display box size, panel options (lines, autoscroll, debug).

server config
none — the machine's window, not maths

The backend machine's window: the agent's specs and its live RAM/VRAM, the model's provenance, and the weights — the offload ratio, load weights / offload, and where the layers sit. Its door is the first row of the Backend ▾ menu (show the server config); press again to hide it — the design runs either way. There is only ever one, it cannot be renamed, and it lives at the top level. Training does not live here any more: it is the training tab of an output box. Designs that still carry an older train node keep working — the engine reads it as the hub.

Fields: display box size, panel options.

Weight bindings — t namespaces

Every box that holds weights carries a binding like t = "models/my.gguf::blk.0.attn_qkv.weight" — a file, and the tensor inside it. This is called a namespace, and two boxes bound to the same namespace share one copy of the weights in memory (the UI marks them with a shared ×N chip). When you load a GGUF, every box is bound for you. When you build by hand, type a name — a free namespace just means the box trains its own weights.

Recipes

Run a GGUF model

  1. Import ▾ → GGUF model … — one pop-up in the middle of the canvas, holding the machine's .gguf files: pick one and load it. Importing adds one nested box in the middle of the view with the file's structure inside — structured exactly like the original implementation — and touches nothing else on the canvas. The list shows every local .gguf: a vision encoder loads on its own too, as a nested box holding its tower (an image port in, an embeds port out). Nothing rides along with a model — load each file you want.
  2. Backend ▾ → connect. Add an input box (or use the skeleton) and press its ▶ run the design. (Give the tokenizer its prompt first: right-click it → set the tokenizer ….)
  3. Double-click the model box to look inside; click boxes to see the numbers that flowed through them.

Train a network on your own data

  1. Build the network inside a model: drop a model (palette → models), double-click it, and build in there — input → embed → one or more layer boxes → whatever produces scores over the vocabulary (a layer sized to the vocab), back out through its output box. Weights are only placeable in here.
  2. Open Palette ▾ → Dataset, drag out the dataset box; give it rows (prompt<TAB>completion or JSONL). A second dataset box is the held-out test split, if you have one.
  3. Drop a train config box (palette → training) and pick the model in its window: that is where every knob lives — the paradigm, the learning rate, the optimizer, the batch, the steps, the optional test split. The dataset box then wires into the config's data dot, and — detecting it — the config names the columns: x col reads the prompt, y col the completion. The plan under the model picker reads the wiring back.
  4. Start the training from the tab's start chip: the full training runs as a task — its progress, curves and detach / resume live there (or via POST /api/tasks below).
  5. Let it run. Detach whenever — the run checkpoints itself and the GPU is free. Days later, resume: same step, same learning rate, same place in the data. This is how you train on monthly GPU credits. Loading the last checkpoint warms a fresh graph with the trained weights — switch back to inference and run it.
  6. Advanced: wire a custom loss — a loss box with the model's scores on its first dot and a dataset on its second. A dataset→loss wire beats the hub's binding: that dataset's rows and that loss run the training instead of the built-in score on the target.
POST /api/tasks
{ "type": "train", "name": "my-run",
  "params": { "batch": 8, "lr": 3e-4, "save_every": 200 },
  "design": { … your canvas as JSON … } }

POST /api/tasks/cmd   { "task": "t_…", "cmd": "save" }     // checkpoint now
POST /api/tasks/cmd   { "task": "t_…", "cmd": "detach" }   // checkpoint + stop
POST /api/tasks/cmd   { "task": "t_…", "cmd": "resume" }   // continue exactly

Train a classifier

  1. A dataset box with rows of text<TAB>label — the text is column A, the label is column B. Held-out rows get a second dataset box.
  2. The network as in the recipe above, ending in a layer sized to the number of classes (inside the model).
  3. The config's window: pick the model, wire the dataset into its data dot, tick y is a class label, and point x col at the text column and y col at the labels — one column, names like cat/dog. The values y takes are the classes: no list to type, and the run reports accuracy (the share of rows the model gets right) alongside the loss, on the train split and the test split.
  4. Start it; watch the accuracy climb to the ceiling the data allows. Freeze the boxes you trust, train the rest.

Train with a reward (rl)

  1. A dataset box of prompts — column A is all the data gives. There is no y column: in rl the reward box is the signal, so a loss box has nothing to do and must not be wired to the dataset.
  2. The network as in the recipe above, ending in the model's output box the policy samples from.
  3. Add a reward box; pick its kind and write it — e.g. expr = "1.0 if output.strip().endswith('!') else 0.0". The score is deterministic — the same output always earns the same reward, so runs are reproducible. Keep it partly soft (a little reward even for imperfect outputs), or the policy can starve on a row that keeps scoring zero.
  4. The config's window: pick the model, set the paradigm to rl and bind the reward box; wire the prompts into the data dot and point x col at them — rl takes x alone, and the policy samples from the model itself. Set temperature, max_tokens and n_samples — how the sampling goes, and how many samples one row of the dataset earns per step.
  5. Start it and watch the reward climb: solid — the mean reward, dashed — its baseline, the policy's decaying average of past rewards. Each step draws n_samples samples from one row, scores each with the reward box, and nudges the policy toward whatever out-earned the baseline. The test split stays idle — every sample the policy draws is scored.

How a network works — just enough

A neural network is a function from numbers to numbers. Text goes in (converted to token ids by the tokenize box), numbers come out (scores for every possible next token). Everything in between is multiplication, addition, and small bends.

One neuron: multiply, add up, bend. A layer is a row of these; a network is layers stacked.

Three ideas cover the rest:

  • Layers and depth. A layer box is a grid of these neurons working on the whole incoming row of numbers at once. Stacked layers make increasingly abstract features — edges, then shapes, then objects; or word patterns, then grammar, then meaning.
  • Embeddings. Tokens are just ids — 52 says nothing about meaning. The embed box turns each id into a vector, a position in a space where "related words live nearby".
  • Logits and sampling. The network's final output is a score (a logit) for every token in the vocabulary. The sample box turns scores into one chosen token — feed it back in, repeat, and the model writes.
Attention — what makes modern language models work — is just these same boxes doing something clever: look at the other tokens, and copy what's relevant (ops like matmul, scale, mask and softmax, right there in the palette). When you load a GGUF model you can see every piece of it.

How training works — just enough

Training is a loop with four moves. Everything else is detail.

Predict, score, nudge, repeat — the whole of training.

The hub: the train config, and the model it names

Training needs one place to say what the model learns from and how. The what is a model box (palette → models): a nested box holding the architecture, the only place trainable weights may live. The how is a train config box (palette → training): it names the model in its window, and holds every knob of the run — the paradigm (supervised | unsupervised | rl), the optimizer, the learning rate, the batch, the steps, the grad clip, the save/eval cadence, the optional test_dataset, whether y is a class label, and in rl the reward box with the sampling knobs.

The data wires into the config's own dot: one matrix, the rows the run reads — a dataset box wired straight in, or a select col box (a dataset's columns, as [rows × columns]). The config detects it: its window lists the columns it hands out, and x col / y col pick the model's input and its target from them (A/B by default; a sequence like x0 x1 x2 is a vector). A training run feeds that batch into the model's first input and scores the model's first output (a wired loss box still wins). An optional test split (bound in the config) is read with the same columns.

What the paradigm means for the signal: supervised scores the model against the y columns (cross entropy — or, when a column spec is a sequence like y0 y1, mean squared error over a vector target); unsupervised needs no y — the model rebuilds the x rows themselves (next-token over their text, or the numbers); rl draws samples from the model and scores them with the reward box. The config's window keeps the plan, the controls and the curves — there is no mode switch: running the design is the input box's ▶ run (inference — an inference run stands the data dot down), training it is this wiring.

A column sequence is a vector: x col x0 x1 x2 feeds the model a 3-wide input (the cells as numbers) and y col y0 y1 a 2-wide target, scored with mean squared error — names come from the matrix's header, letters like A/B stand for positions within the columns it hands out, and a blank spec takes the first (x) and second (y) column. The server config box — the Backend ▾ menu's first row — stays the machine's window. Designs built before models — weights flat on the canvas, the config boxed into an input, the fields stored on an output — keep working as they did; the wrap moves them over when you want.

One exception, for the veterans: wire a loss box from a dataset the way the old designs did, and that wire beats the config — that dataset and that loss run the training.

While a training task runs, the canvas shows the config, the model it names, the data the training reads from, and — in rl — the reward box that does the scoring.

The vocabulary of training

  • Loss — one number saying how wrong the model was on this batch: compare the model's output with what the dataset box's y column says should have come out. The training tab's built-in score (cross entropy, the one so far) does that against the output it trains on; a wired loss box computes its own.
  • Gradient — for every weight: if this weight were a little higher, would the loss go up or down, and by how much? Computed automatically (backpropagation) from the loss.
  • Step — nudge every weight in the direction that lowers the loss. The learning rate (lr) is the size of the nudge: too small crawls, too large thrashes. Step counts in the training tab are literally this.
  • Batch — the handful of rows scored per step. Bigger batches give steadier nudges; smaller ones move faster per wall-clock minute.
A healthy loss curve: steep at first, then flattening. If it rises, the learning rate is too big; if it never moves, too small.

Checkpoints: pause and continue

A training run is long, and GPU time is billed by the hour — so the app treats stopping as a first-class move. A checkpoint is a saved snapshot: the trainable weights, the optimizer's state, and the step counter.

  • Save now — land a checkpoint where the run stands.
  • Detach — checkpoint and stop cleanly. The GPU is free. (Distinct from hold, which stops stepping but keeps the machine.)
  • Resume — load the checkpoint and continue: same step, same learning rate, same place in the data. To the loss curve, nothing happened.
Detach frees the GPU; resume continues bit for bit. This is how a run survives monthly credit limits.

Three ways to train

  • Supervised — you hold the answers: the output's training tab names the dataset and the x/y columns; the output itself is what the model is scored on, and the loss measures the distance from your answers. The paradigm's default — simplest, and the right first thing to try.
  • Reinforcement (RL) — no answers, only a score. The training tab's paradigm is rl: the model samples outputs from the output it trains on, the reward box it names scores them, and training nudges the model toward higher scores. Use it when "good" is easy to check but hard to write out (passes the tests, ends with a period, matches the schema).
  • RLHF — reinforcement learning from human feedback: people compare outputs (this one better than that one), and training treats those comparisons as the reward. The same rl paradigm — today the score comes from a reward box; the human-feedback channel is on the way.

Weights & saving

  • A design is not its weights. The JSON describes the boxes and their wiring. Weights live separately: in a model file you loaded (.gguf, safetensors), or created by training (checkpoints).
  • Namespaces bind them. Each weighted box's t says which file and tensor its weights come from. Boxes sharing a namespace share one in-memory copy — that's how a 27B model fits sensibly.
  • Frozen boxes may run quantized (smaller, faster, numerically exact to the reference). Boxes you train stay full precision (f16/f32) — training on quantized weights is how models quietly rot.
  • Checkpoints are portable. A checkpoint directory holds the trainable weights, the optimizer state, and metadata; copy it between machines and resume works there.

The backend's HTTP API — runs, models, tasks — is documented in docs/backend.md in the repository.

Your first session

Fifteen minutes, no GPU required (CPU is fine for this one):

  1. Meet the canvas — open Palette ▾, drop a model (the models category) and double-click into it. In there, drag out an input, an embed (vocab 64, dout 16), a layer (din 16, dout 64), and wire them in that order into its output box. Back out — the model now hands out the layer's logits.
  2. Teach it a tiny language — add a dataset box with a handful of rows, e.g. a c / b d / c d (type them as prompt<TAB>completion), with vocab abcd. A detokenize box wired from the model reads the text back.
  3. Add the loss — a loss box; wire the model's output into dot one, the dataset into dot two.
  4. Watch it learn — drop a train config (palette → training), pick the model in its window, wire the dataset into its data dot, and start from the start chip. The task's readout should show the loss falling within seconds — the network has learned that a is followed by c.
  5. Detach, then resume — press detach; watch it checkpoint and stop. Press resume; the step counter continues where it stopped.
Then go big. Load a real model (Import ▾ → GGUF model …), connect the backend, and run a prompt. Double-click into the model and find the boxes you now understand: embeds, layers, norms, ops — same vocabulary, billion-scale.

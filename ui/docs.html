What nnstudio is

nnstudio is a workbench for neural networks. You compose a network on a canvas out of boxes — each box is one piece (an embedding table, a matrix multiply, an activation, a tokenizer…), and wires between boxes carry the data. When you run the canvas, numbers flow along the wires, box by box, and whatever comes out of the last box is the answer.

The same canvas does both jobs: it runs a network (feed it text or numbers, watch the outputs) and trains one (give it a dataset and a loss, and it improves its boxes). A canvas is stored as plain JSON — a design — so you can save it, share it, and load it back exactly as it was.

Three things make the app practical rather than toy:

  • Real models. Point a GGUF box at a .gguf file (or an hf box at a Hugging Face repo) and the app builds the whole network for you — hundreds of boxes, wired exactly like the model's original implementation. You can then look inside it, change it, or train on top of it.
  • A real backend. The heavy maths runs on a backend service (your GPU, CPU, or a remote machine) — the browser only draws and edits. The Backend ▾ menu connects them.
  • Tasks. Long work — training, big jobs — runs as a task managed through the agent box: it shows progress live, and can be paused, detached (checkpointed and stopped), and resumed later.
The rest of this handbook is two halves: everything about using the app (the canvas, the boxes, recipes), then two short theory sections — how networks work and how training works — written just deep enough for the boxes to make sense. If you already know what a loss is, skim them.

The canvas: using it

The toolbar strip above the canvas has five menus: Files ▾ Palette ▾ Backend ▾ Run ▾ VRAM ▾

Moving around

  • Add a box — open Palette ▾, expand a category, and drag a card onto the canvas. Categories follow the boxes' jobs: containers, data, compute, results, system.
  • Add training data — the Palette's Dataset ▾ category holds the dataset box. Right-click it any time to set the rows ….
  • Move / resize — drag a box by its body; drag its corner to resize (boxes with displays, like the agent box, resize with their display).
  • Wire two boxes — drag from a box's right dot (its output) to another box's left dot (its input). Right-click a wire to reshape or remove it.
  • Edit a box — right-click it. Its menu renames it, changes its settings (the activation, the operation, the embedding…), and offers freeze (keep its weights fixed) and off (skip it on runs).
  • Step inside a nested box — double-click a custom box. A nested box is a whole network of its own — that's the "nested" in nnstudio. Double-clicking again goes deeper; the strip above the canvas shows where you are and takes you back.
  • Run it — connect Backend ▾ first, then Run ▾. Each run leaves its numbers on the boxes (click a box to see the values that passed through it).
  • Price it — VRAM ▾ shows how much memory the design's weights need and where they will live (GPU or system). Freeze nothing, move everything, see it change.
The whole idea, in one line: boxes hold the pieces, wires carry the numbers.

Designs, saving, sharing

Everything on the canvas is a design — plain JSON. Files ▾ exports it (a .json file), imports one back, and lists what's saved. Design JSON nests: a nested box carries its own network inside the file, so one file can hold a whole model. The canvas also auto-saves in the browser — reload and your work is still there.

The boxes: reference

Every box shows its name, its shape (what comes in and goes out), and — if it holds weights — its weight count. Below: what each box does, the fields you can set (right-click → set …), and what wires into or out of it.

Data boxes — getting things in

input
0 in · 1 out

Where data enters the network: text, numbers you type, or generated values. An input box is what a run feeds — one per thing you want to test.

Fields: width dout; mode input_mode — text (type a prompt), python (a small expression for the values), or random; the text or code itself; input_rows for batches.

tokenize
1 in (text) · 1 out (ids)

Turns text into token ids — the numbers a network actually reads. With a wire in, it tokenizes whatever arrives; without one, its own text.

Fields: repo (a Hugging Face tokenizer) or vocab (a simple one-character-per-token vocabulary, great for teaching); optional default text.

dataset
0 in · 1 out (labels → loss)

Your training data. Each row is a prompt and a completion — what the model reads, and what it should learn to write. A training run feeds its rows to the loss box; the prompt part of each row is masked out of the loss (the model learns to produce the completion, not to parrot the prompt).

Its face is a dataframe sheet inset in the card, like a pandas table or a CSV: column letters, editable column names (empty names are fine), and a type chip per column (int64, float64, bool, object, image, video) — inferred from the values, click to override. Click a cell to type (Enter moves down, Tab right), paste a block from Excel/Sheets, + row / × manage rows, the letter strip's + / × manage columns, and dragging the header edge resizes one. Double-click the box for more room.

A column can hold images and videos: drop a file on a cell (or paste one) — the bytes live in the project's media store, the cell carries only a small blob: reference, and the table shows the thumbnail (click to view or play). The box menu exports the table: a plain .csv for text and numbers, or a .zip (csv + media) when cells hold media — and imports either back. A file-backed dataset previews its first rows (read-only) from the backend.

Fields: text (rows typed in) or file (a JSONL file path on the backend machine); tokenizer repo/vocab, like the tokenize box. One row per line: JSON like {"prompt": "…", "completion": "…"}, or prompt<TAB>completion. The sheet keeps both formats verbatim — JSON rows keep their extra keys.

Compute boxes — the network itself

embed
1 in (ids) · 1 out (vectors)

A lookup table: every token id becomes a learned vector. It is the bridge from discrete tokens to the continuous numbers the rest of the network works in. (Word embeddings are the classic "what does this word mean as a direction in space" representation.)

Fields: vocab (table rows), din/dout (vector width), embed_scale (Gemma-style scaling); the weight binding t and dtype.

layer
1 in · 1 out

The workhorse: multiply the incoming numbers by this box's weight matrix (plus a bias). Stack enough layers and the network can fit very complicated patterns. This is where nearly all of a model's weights live.

Fields: din/dout; weight binding t; dtype. Uncheck nothing — a layer not frozen is trainable.

act
1 in · 1 out

An activation — a small bend applied to every number. Without one, a stack of layers collapses into a single layer; activations are what give depth its power. Attention scores also pass through here.

Fields: the function act (silu, relu, tanh, softmax…); gain (a scaling factor, e.g. attention's 1/√d); causal (a "never look at future tokens" mask).

norm
1 in · 1 out

Keeps the numbers flowing through the network on a sane scale (deep networks drift into huge or tiny values otherwise). Every modern model sprinkles these between its compute boxes.

Fields: norm — rms or layer; eps; size; zc.

op
1–2 in · 1 out

One mathematical operation — anything else the network needs. Two-input ops (add, matmul, concat…) take wires into both dots; one-input ops take one.

Fields: the operation op: transpose, dot product, matmul, concat, add, subtract, multiply, divide, rope, scale, topk, conv1d, scan, reshape, permute, repeat, mask, slice, zeros; plus each op's own settings (dims, axes, theta, window, head geometry for attention…).

script
1 in · 1 out

A box you program yourself: a short Python expression over its input (x) returning a tensor. The escape hatch for anything the other boxes don't cover. The code travels inside the design file.

Fields: script.

custom
its own · 1 in · 1 out

A nested box: a whole network inside one box. Double-click to step in and edit its insides; from outside it behaves like a single box. This is how large models stay legible — a 27-billion-parameter model is one GGUF box that you can open into blocks, each block open into its attention and MLP.

Fields: its inner network; when it was built from a model file: gguf and the source repo. A GGUF box (Palette ▾ → containers) is a custom box that loads a whole .gguf model — right-click → Load GGUF ….

Result boxes — getting things out

output
1 in · 0 out

The end of the line: whatever reaches it is shown as the run's result. Name outputs after what they are (logits, hidden) — runs report per output name.

Fields: din, its name.

detokenize
1 in (ids) · 1 out (text)

Token ids back into text — the inverse of the tokenize box. Put it after a sample box to read what the model produced.

Fields: repo/vocab — must match the tokenize box that fed the model.

sample
1 in (logits) · 1 out (ids)

Picks the next token from the model's scores (logits). This one box is the difference between "a network that computes" and "a model that writes": generation is sampling a token, feeding it back in, and repeating.

Fields: temperature (0 = always take the best token; higher = more adventurous), sample_seed (reproducible picks).

loss
2 in (logits, labels) · 1 out (scalar)

Measures how wrong the model is — one number, lower is better. It compares the model's scores against a dataset box's labels. During training this is the number that falls. Its output is a plain scalar, so you can wire it anywhere and watch it.

Fields: loss (the kind — cross-entropy for next-token prediction).

reward
0 in · scores texts

A deterministic score for a piece of text — "how good was this output?". It doesn't run inside the dataflow; a training run applies it to generated samples. The same pair of prompt and output always earns the same score: exact match against a target, a regex pattern, a length budget, or your own Python expr over prompt and output. This is the hook for reinforcement learning: the reward says how good, the training raises it.

Fields: reward (python/exact/regex/length), expr, pattern, match, limit.

System boxes — models and long work

hf
0 in · text result

A complete Hugging Face model, run by the backend as a whole — no wires needed. The quick way to get a baseline answer (or a reference for your own canvas to match).

Fields: repo, a prompt text, temperature.

agent
none — a window, not maths

A live window onto a task — a long-running job managed by the backend agent (research, big jobs). It shows the task's stream as it works, with its progress ring on the card. This is the app's one surface for firing and managing tasks: start one here, pause it, cancel it, read what it did. Double-click the box to grow or shrink its display.

Fields: task_id (its task), display box size, panel options (lines, autoscroll, debug).

train
none — a display, not maths

The training window: step counter, live loss and its curve, the latest checkpoint, and the controls that matter when a GPU's clock is ticking — save now (land a checkpoint where it stands), detach (checkpoint and stop cleanly, freeing the GPU), resume (continue exactly where it stopped), hold (stop stepping but keep the machine). Bind it to a training task's task_id and it follows that run.

Fields: task_id, display box size, panel options.

Weight bindings — t namespaces

Every box that holds weights carries a binding like t = "models/my.gguf::blk.0.attn_qkv.weight" — a file, and the tensor inside it. This is called a namespace, and two boxes bound to the same namespace share one copy of the weights in memory (the UI marks them with a shared ×N chip). When you load a GGUF, every box is bound for you. When you build by hand, type a name — a free namespace just means the box trains its own weights.

Recipes

Run a GGUF model

  1. Palette ▾ → containers → GGUF box (a whole model loads at the top level).
  2. Right-click it → Load GGUF … → pick your .gguf file. (The first click arms the overwrite — click again to confirm.) The box fills with the model's blocks, wired exactly like the original implementation.
  3. Backend ▾ → connect. Run ▾ → type a prompt → run.
  4. Double-click the GGUF box to look inside; click boxes to see the numbers that flowed through them.

Train a network on your own data

  1. Build the network: input → embed → one or more layer boxes → whatever produces scores over the vocabulary (a layer sized to the vocab).
  2. Open Palette ▾ → Dataset, drag out the dataset box; give it rows (prompt<TAB>completion or JSONL).
  3. Add a loss box. Wire the model's scores into its first dot, the dataset box into its second.
  4. Add a train box.
  5. Start a training task with this design — ask the agent box to do it, or POST it to the tasks API (below). The train box shows the step count, the loss, and the curve as it happens.
  6. Let it run. Detach whenever — the run checkpoints itself and the GPU is free. Days later, resume: same step, same learning rate, same place in the data. This is how you train on monthly GPU credits.
POST /api/tasks
{ "type": "train", "name": "my-run",
  "params": { "batch": 8, "lr": 3e-4, "save_every": 200 },
  "design": { … your canvas as JSON … } }

POST /api/tasks/cmd   { "task": "t_…", "cmd": "save" }     // checkpoint now
POST /api/tasks/cmd   { "task": "t_…", "cmd": "detach" }   // checkpoint + stop
POST /api/tasks/cmd   { "task": "t_…", "cmd": "resume" }   // continue exactly

Score outputs with a reward

  1. Add a reward box; pick its kind and write it — e.g. expr = "1.0 if output.strip().endswith('.') else 0.0".
  2. Training runs score generated samples with it. The score is deterministic — the same output always earns the same reward, so runs are reproducible.
  3. Watch rewards climb alongside the loss on the train box. Higher reward is the reinforcement-learning objective; lower loss is the supervised one.

How a network works — just enough

A neural network is a function from numbers to numbers. Text goes in (converted to token ids by the tokenize box), numbers come out (scores for every possible next token). Everything in between is multiplication, addition, and small bends.

One neuron: multiply, add up, bend. A layer is a row of these; a network is layers stacked.

Three ideas cover the rest:

  • Layers and depth. A layer box is a grid of these neurons working on the whole incoming row of numbers at once. Stacked layers make increasingly abstract features — edges, then shapes, then objects; or word patterns, then grammar, then meaning.
  • Embeddings. Tokens are just ids — 52 says nothing about meaning. The embed box turns each id into a vector, a position in a space where "related words live nearby".
  • Logits and sampling. The network's final output is a score (a logit) for every token in the vocabulary. The sample box turns scores into one chosen token — feed it back in, repeat, and the model writes.
Attention — what makes modern language models work — is just these same boxes doing something clever: look at the other tokens, and copy what's relevant (ops like matmul, scale, mask and softmax, right there in the palette). When you load a GGUF model you can see every piece of it.

How training works — just enough

Training is a loop with four moves. Everything else is detail.

Predict, score, nudge, repeat — the whole of training.

The vocabulary of training

  • Loss — one number saying how wrong the model was on this batch. The loss box computes it: compare the model's scores with what the dataset box says should have come out.
  • Gradient — for every weight: if this weight were a little higher, would the loss go up or down, and by how much? Computed automatically (backpropagation) from the loss.
  • Step — nudge every weight in the direction that lowers the loss. The learning rate (lr) is the size of the nudge: too small crawls, too large thrashes. Step counts on the train box are literally this.
  • Batch — the handful of rows scored per step. Bigger batches give steadier nudges; smaller ones move faster per wall-clock minute.
A healthy loss curve: steep at first, then flattening. If it rises, the learning rate is too big; if it never moves, too small.

Checkpoints: pause and continue

A training run is long, and GPU time is billed by the hour — so the app treats stopping as a first-class move. A checkpoint is a saved snapshot: the trainable weights, the optimizer's state, and the step counter.

  • Save now — land a checkpoint where the run stands.
  • Detach — checkpoint and stop cleanly. The GPU is free. (Distinct from hold, which stops stepping but keeps the machine.)
  • Resume — load the checkpoint and continue: same step, same learning rate, same place in the data. To the loss curve, nothing happened.
Detach frees the GPU; resume continues bit for bit. This is how a run survives monthly credit limits.

Three ways to train

  • Supervised — you hold the answers: dataset rows of prompt + completion. The loss measures distance from your answers. Simplest, and the right first thing to try.
  • Reinforcement (RL) — no answers, only a score. The model produces outputs, the reward box scores them, and training nudges the model toward higher scores. Use it when "good" is easy to check but hard to write out (passes the tests, ends with a period, matches the schema).
  • RLHF — reinforcement learning from human feedback: people compare outputs (this one better than that one), and training treats those comparisons as the reward. For when "good" is a matter of judgment.

Weights & saving

  • A design is not its weights. The JSON describes the boxes and their wiring. Weights live separately: in a model file you loaded (.gguf, safetensors), or created by training (checkpoints).
  • Namespaces bind them. Each weighted box's t says which file and tensor its weights come from. Boxes sharing a namespace share one in-memory copy — that's how a 27B model fits sensibly.
  • Frozen boxes may run quantized (smaller, faster, numerically exact to the reference). Boxes you train stay full precision (f16/f32) — training on quantized weights is how models quietly rot.
  • Checkpoints are portable. A checkpoint directory holds the trainable weights, the optimizer state, and metadata; copy it between machines and resume works there.

The backend's HTTP API — runs, models, tasks — is documented in docs/backend.md in the repository.

Your first session

Fifteen minutes, no GPU required (CPU is fine for this one):

  1. Meet the canvas — open Palette ▾, drag out an input, an embed (vocab 64, dout 16), a layer (din 16, dout 64), and a detokenize. Wire them in that order.
  2. Teach it a tiny language — add a dataset box with a handful of rows, e.g. a c / b d / c d (type them as prompt<TAB>completion), with vocab abcd.
  3. Add the loss — a loss box; wire the layer's output into dot one, the dataset into dot two.
  4. Watch it learn — add a train box, then start a training task with the design (ask the agent box: "train the current design"). The curve on the train box should fall within seconds — the network has learned that a is followed by c.
  5. Detach, then resume — press detach; watch it checkpoint and stop. Press resume; the step counter continues where it stopped.
Then go big. Drop a GGUF box on the canvas, load a real model (click the overwrite twice), connect the backend, and run a prompt. Double-click into the model and find the boxes you now understand: embeds, layers, norms, ops — same vocabulary, billion-scale.
